# 0.4 性能检查清单

性能按一个整体来看，包含三部分：
- 占用：Glance 运行时占用的处理器、内存和显卡资源。
- 速度：每个窗口和页面打开、关闭、切换所需的时间。
- 流畅度：拖动改变大小或移动时是否卡顿。

三部分都要在改动前测出基线，改动后用同一方法复测，并把前后数字写进本文末尾的记录。只报占用数字不算完成。

## 一、原则

1. **先测量，后改动。** 每一项改动都要对应一个测得的问题。没有数据支持的“优化”不做。
2. **自动化，可重复。** 测量由程序驱动，每项至少重复 20 次，记录中位数、p95 和最大值。不靠手点、不靠肉眼。
3. **区分冷启动和热启动。** 冷：线程、图形设备、窗口、表面、场景都是首次创建。热：同一会话内再次打开。两种分别记录。
4. **以显示器刷新间隔为尺度。** 测量时记下显示器的刷新率（144 Hz 下一帧是 6.9 ms，60 Hz 下是 16.7 ms）。流畅度以“是否在一个刷新间隔内交出一帧”来判断，不以固定毫秒数判断。
5. **测正式配置。** 用 release 配置编译，不带 studio 功能（测量工具本身单独编译），关闭调试日志。
6. **不碰游戏进程。** 帧率只从 ETW 取，不打开游戏的进程（反作弊程序会对此作出反应）。测量结束后停止所有调试用的 ETW 会话（`logman stop Glance.Frames.Debug -ets`）。

## 二、测量环境

| 环境 | 用途 |
| --- | --- |
| 主力机（9950X，RTX 5070 Ti，144 Hz） | 主要基线。高配机器上的问题在低配机器上只会更重。 |
| 干净虚拟机 Win11 与 Win10（WARP 软件绘制） | 最差情况：没有显卡，全部绘制由处理器完成。用来暴露每帧绘制量过大的问题。 |
| 核显机器（如有，或借助用户诊断报告） | 显存与带宽受限的情况。用户报告里的“Drawn on”一行用于对照。 |

每个环境记录：Windows 版本、显示器分辨率与缩放、刷新率、壁纸、外观设置（玻璃、毛玻璃程度、皮肤）。玻璃与非玻璃两种外观都要测，因为玻璃需要截取桌面并做模糊。

## 三、占用

### 3.1 测什么

每个进程（glance.exe、glance-sensors.exe、glance-remote.exe）分别记录：
- 处理器：一段时间内的累计 CPU 时间换算成平均占用率，以及每秒唤醒次数（上下文切换数）。唤醒次数决定笔记本能否进入低功耗状态，比平均占用率更能说明“空闲是否真的空闲”。
- 内存：专用工作集与提交大小（private bytes）。持续运行 1 小时与 8 小时后各取一次，检查是否只增不减。
- 显卡：进程的专用显存与共享显存（PDH `GPU Process Memory`），以及 3D 引擎占用率（PDH `GPU Engine`）。
- 句柄、GDI 对象、用户对象、线程数：长时间运行后检查是否增长。

| 编号 | 场景 | 持续 |
| --- | --- | --- |

| U2 | 面板展开并停留（玻璃与非玻璃各一次） | 2 分钟 |
| U3 | 桌面上放 1 个、3 个、6 个组件，其中包括音乐组件与工作台组件 | 10 分钟 |
| U4 | 音乐播放中，歌词窗口与律动条显示 | 10 分钟 |
| U5 | 音乐全屏显示 | 5 分钟 |
| U6 | 游戏中，悬浮窗显示（用一个自制的全屏 D3D 测试程序代替真实游戏） | 10 分钟 |
| U7 | 设置窗口打开并停在每一页上（每页 30 秒） | 约 4 分钟 |
| U8 | 手机遥控连接中，手机页面在前台刷新 | 5 分钟 |

### 3.3 要特别检查的点

- 面板收起、没有任何窗口显示时，界面线程是否完全不醒（没有空转的计时器，没有不必要的重绘）。
- 每个窗口只在内容变化时重绘。读数没变化时不应重画整个窗口。
- 隐藏的窗口是否按 `life.rs` 的规则交还表面与缓存。3 秒后显存是否回落。
- 截取桌面（scene）的捕获池只增不减的问题（见 architecture.md 的“What drawing holds”一节）：多次改变大小后显存是否停在可接受的上限。
- 传感器进程的读取周期与采样间隔是否一致，读不到的传感器是否仍在每次重试。
- 歌词与律动条：没有声音时律动条是否停止取样和重绘。
- 剪贴板记录：大图片是否被完整保存在内存中，还是只存缩略图与文件。

## 四、速度（打开、关闭、切换）

### 4.1 怎么计时

在程序内部计时，从触发开始，记录三个时间点：
1. 触发：按键、鼠标抵达屏幕边缘、点击，或程序内部发出的命令。
2. 首帧交出：第一帧提交给合成器（DComp `Commit`）。
3. 稳定：入场动画结束，最后一帧提交。

需要的话，用 `DCompositionGetFrameStatistics` 或 DWM 的帧统计确认首帧在哪一次刷新时真正上屏。

计时结果写入一个测量文件，不写入用户日志。测量用的驱动程序在 studio 功能下编译，可以按脚本依次打开、关闭、切换各窗口，并重复多次。

### 4.2 项目

| 编号 | 操作 | 记录 |
| --- | --- | --- |
| S1 | 面板打开：推屏幕边缘、停留触发、快捷键各一次 | 冷与热的首帧、动画完成。其中截取桌面所用时间单独列出（用户报告里有 212 ms 的情况） |
| S2 | 面板关闭：移开、点击别处、按 Esc | 首帧与窗口隐藏时间 |
| S3 | 面板内部：展开或收起一个模块、切换游戏与日常模式 | 首帧时间 |
| S4 | 设置窗口打开：冷（线程与图形设备都要新建）与热 | 首帧时间与第一帧绘制用时（用户报告里有 36 ms 与 19 秒的帧） |
| S5 | 设置窗口内切换：七个页面两两切换，监控页的三个标签之间切换，展开或收起每一个模块卡片 | 每次切换的首帧与最长一帧 |
| S6 | 设置窗口关闭 | 窗口消失时间，以及图形设备交还所用时间 |
| S7 | 组件：从面板撕下一个模块、撕下整个面板、两个组件合并、拆开、关闭 | 首帧与动画完成 |
| S8 | 音乐全屏：打开与关闭 | 首帧与动画完成 |
| S9 | 悬浮窗：游戏开始后出现、游戏结束后消失 | 从检测到游戏到悬浮窗首帧的时间 |
| S10 | 侧边页（beside）、菜单、提示框、对话框：打开与关闭 | 首帧时间 |
| S11 | 便签：呼出、输入第一个字、关闭 | 呼出到首帧，按键到字出现 |
| S12 | 程序启动：从进程开始到托盘图标出现，到第一次可以打开面板 | 两个时间 |
| S13 | 睡眠唤醒、锁屏解锁、显卡重置（Win+Ctrl+Shift+B）之后，面板与组件恢复 | 恢复到正常绘制的时间 |

### 4.3 要特别检查的点

- 冷打开慢的原因：是新建图形设备、新建窗口、加载字体、截取桌面，还是第一次排版。逐项分开计时。
- 切换页面时是否重建了不必要的东西（文本布局、图片、效果）。
- 是否有在界面线程上同步等待的操作（读注册表、计划任务、WMI、网络、磁盘、命名管道）。
- 设备丢失后是否反复重建设备（19 秒那一帧的报告前后都有“设备丢失”）。

## 五、流畅度（改变大小与移动）

### 5.1 怎么计时

在拖动过程中逐帧记录：
- 每帧的绘制用时，分成排版、截取桌面、绘制、交给合成器四段（组件已有这样的分段日志）。
- 相邻两帧提交的间隔。
- 掉帧数：在一个刷新间隔内没有交出新帧的次数。

拖动由测量驱动按固定轨迹模拟：匀速拉大 1 秒、匀速缩小 1 秒、来回抖动 1 秒。每种重复 20 次。

### 5.2 项目

| 编号 | 操作 |
| --- | --- |
| R1 | 设置窗口拖边框改变大小（系统的移动与改变大小循环） |
| R2 | 设置窗口拖动位置 |
| R3 | 组件改变大小：音乐组件、监控组件、工作台组件、合并后的组件 |
| R4 | 组件拖动位置，包括贴边与吸附 |
| R5 | 面板改变大小 |
| R6 | 歌词窗口的移动与改变大小 |
| R7 | 布局页里拖动组件到屏幕边缘的预览 |
| R8 | 设置窗口在两个缩放不同的显示器之间拖动 |

每项分别测玻璃与非玻璃外观。

### 5.3 要特别检查的点

- 每帧是否重新截取桌面并重新模糊。拖动中能否复用已截取的图像。
- 改变大小时是否每帧新建表面或位图。`Gfx::settle` 与暂存位图只增不减的策略是否生效。
- 文本排版缓存在尺寸连续变化时的命中率。
- 拖动中是否有同步保存设置到磁盘的操作。
- 合成器侧：表面尺寸变化是否导致闪烁或空白一帧。

## 六、目标

以下数值是初步目标，基线测出后再确认：

| 项目 | 目标 |
| --- | --- |
| U1 空闲 | 平均处理器占用 < 0.1%，界面线程每秒唤醒 < 2 次，传感器进程每个采样间隔唤醒一次 |
| U3 组件 | 读数每秒更新一次时，平均处理器占用 < 0.5% |
| 内存 | 8 小时内不持续增长，窗口隐藏后 3 秒内交还显存 |
| S1 面板热打开 | 首帧 < 50 ms |
| S1 面板冷打开 | 首帧 < 150 ms |
| S4 设置窗口热打开 | 首帧 < 100 ms |
| S5 页面切换 | 首帧在 1 个刷新间隔内，最长一帧不超过 2 个刷新间隔 |
| R 系列改变大小 | p95 帧间隔不超过 1 个刷新间隔，掉帧率 < 2% |

虚拟机（软件绘制）不设同样的目标，只要求没有超过 100 ms 的帧，并记录与主力机的差距。

## 七、工具

- 测量驱动：studio 功能下新增一个命令，按脚本执行 S 与 R 系列操作，结果写成 CSV。
- 占用采集：一个独立的脚本，用 PDH 与 `GetProcessTimes`、`GetProcessMemoryInfo`、`GetGuiResources` 按秒采样三个进程。
- 已有工具：`glance --widget-frames`（组件逐帧计时）、`glance --surface-memory`（表面显存）、日志里的“panel: opened in”和“a frame took”。
- 对照：Windows Performance Recorder 的 CPU 采样与 GPU 活动，用于定位热点。用完停止会话。

主人的实际配置（一个条形组件，玻璃，实时背景，背后是动态壁纸）在探针里测得：

| 项目 | 0.3.13 正式版 | 0.4 探针 |
| --- | --- | --- |
| 处理器（全部线程） | 131 ms/s | 119 ms/s（含本进程采样 15.6 ms/s） |
| 面板线程 | 72 ms/s | 49 ms/s |
| 显存 | 470 至 495 MB | 291 至 329 MB |

组件每秒重绘约 23 次，与背后读到新画面的次数一致，没有白画的帧。每帧绘制约 2 ms。

显存的大头是桌面本身的截取：动态壁纸画在桌面窗口的子窗口里，桌面窗口的缩略图里没有它，只能截取整个桌面窗口。截取按桌面外框建池，5600×3840 每帧 86 MB，池里两帧共 172 MB，连同系统一侧的开销约 250 MB（关掉这一截取对照测得 44 MB）。两帧是持续截取的下限（一帧留作新区域的来源，另一帧给系统写入），截取池重建又会泄漏一帧，所以这部分保留。没有动态壁纸、或只有一块屏幕时，这一项相应小得多。没有组件时显存为 12.4 MB。

换成不看桌面的外观（记录纸）后，这些截取以前一直留到退出：玻璃下打开过面板再换成记录纸，显存仍是 277 MB。自 48469d2 起，换外观时面板、组件、便签页的背景画面随之释放，最后一个画面释放时桌面截取也结束，实测降到 105.7 MB。剩下比一开始就用记录纸（21 MB）多出的约 85 MB，是系统给建过的那个截取池记的账，Glance 重启后消失。

### 8.4 泄漏

- 空闲 60 秒：内存 115.0 至 116.9 MB，显存始终 12.4 MB，线程数回落。
- 设置窗口打开关闭 3 次：每次关闭后线程数回到原值，内存回到约 129 MB，显存 12.4 MB 不变。
- 主人配置连续 20 秒：显存中位数与最大值相同，没有增长。
